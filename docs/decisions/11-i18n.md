# Phase 11 — i18n

How the site is served in English and Spanish with Polylang free. The editorial
rule (every note exists in both languages) is in [10](10-notes.md).

See [README.md](README.md) for how entries are written.

## 2026-10-21 — URLs: translated bases, no `-es` suffix

English is the default language and has no prefix; Spanish lives under `/es/`
(Polylang directory mode). Polylang free does not translate the base of a post
type, and it cannot share a slug between two languages (the duplicate gets
`-es`). The plugin adds a small layer on top (`plugin/inc/i18n.php`):

- **Bases:** `/es/trabajo/`, `/es/servicios/` and `/es/notas/` for projects,
  services and notes. The map is filterable (`portfolio_core_url_bases`).
- **No `-es` in public URLs:** a Spanish post keeps its `-es` slug in the
  database only when it would otherwise clash. The public URL drops it when the
  shorter slug equals the English post's slug; the request is resolved back to
  the real post.
- **Output and input:** `post_type_link` / `post_link` build the Spanish URL,
  rewrite rules (`top`, because Polylang does not prefix them) accept it, and a
  301 sends the old English base under `/es/` to the translated one.
- **hreflang:** Polylang's tags plus `x-default` pointing to English.
- **Root:** the language root is `home_url( '/es/' )`, not `pll_home_url()`,
  which returns the static front page (`/es/inicio/`) and would duplicate it in
  every URL.

Cost: a layer of our own rewrite code that Polylang Pro would make unnecessary.

## 2026-10-21 — Language switcher in the header

The switcher sits in the header next to the theme toggle (`EN / ES`). It links
to the translation of the current page, falls back to the language's home when
there is none, marks the current language with `aria-current` and gives the
full language name to screen readers.

## 2026-10-21 — Related block resolves the translation at render time

The block stores the ID of the service and project in the default language. On
render, the plugin maps each ID to its translation in the current language
(`pll_get_post`). **If there is no translation, the row is skipped** rather than
showing a card in another language. A Spanish note therefore shows no Related
block until its service has a Spanish version.

## 2026-10-21 — Plugin translations: front-end strings only

`portfolio-core` loads `languages/es_ES` for the three strings the visitor sees
(Related, Service, Project). The admin UI of the plugin stays in English.
`.mo` and `.l10n.php` are committed next to the `.po`, like the theme's.

## 2026-10-21 — Canonical of the front page

Rank Math's Polylang support appends the Polylang home path to the front page
canonical, assuming WordPress at the domain root; in a subfolder the path is
repeated. The plugin sets the front page canonical to `pll_home_url()` of the
current language, the same URL the hreflang tags use, so canonical, `og:url`
and hreflang always agree. The Notes page has its own correction (see 10).

## 2026-10-21 — Breadcrumb Home label comes from the theme catalogue

Rank Math has a single "Home" label for every language. The breadcrumb filter
now sets it from the theme's translation (`Home` → `Inicio`), so the visible
trail and the `BreadcrumbList` schema are in the page's language.

## 2026-10-21 — Parity: everything exists in both languages

Gonzalo's rule: every public item exists in English and Spanish and is linked
as a translation: pages, notes, projects, services, categories and menus.
Spanish URLs follow the table in the sitemap (`/es/trabajo/`,
`/es/servicios/desarrollo-wordpress/`, `/es/privacidad/`…).

- **Same structure first, text with its translation:** an item is created in
  Spanish with the English fields copied, so the template and layout are
  tested straight away. Copied English text is pending, not translated, and
  must not go live under `/es/`.
- **Menus are separate per language** (Polylang free): `Main ES` is the
  Spanish primary menu. Items point to the pages themselves, not to custom
  URLs, so they follow each language's permalink and the install's location.
- **Same slug in both languages** (e.g. Cookies): Polylang free adds a suffix
  to the second one. The Spanish page is saved as `cookies-es`; the plugin
  links it without the suffix, resolves `/es/cookies/` to it and redirects
  `/es/cookies-es/` there, like it does for notes and projects.

## 2026-10-21 — Parity: the one exception and the menu fix

- **Design system is English only.** It is a technical page, `noindex` and out
  of the sitemap; a Spanish copy adds nothing. It is the only page without a
  translation.
- **Test content removed:** WordPress's sample page and the placeholder and
  test posts were trashed, so every remaining post and page has its pair.
- **The English main menu uses pages too.** Its items were custom links with
  the local URL typed in, which would break in production. They now point to
  the pages, like the Spanish menu.

## 2026-10-21 — Spanish text is a translation of the English, reviewed later

The Spanish copy is translated from the English as it stands, so every page is
complete in both languages; Gonzalo then edits it into his own Spanish.

- **What was translated:** the real text of the pages, services and resume, and
  the theme's strings (`es_ES.po`, 121 messages). Placeholder text (Lorem ipsum
  in the legal pages, the case page "How this site is built" and some service
  fields) is not translated: it is replaced in both languages when it is
  written.
- **Not translated:** the Design system page (English only) and the proper
  names (clients, projects, tools).
- **Field limits apply to the Spanish too.** SCF refuses to save a whole page
  when one text field is over its `maxlength`, and gives no message in the
  editor form: the page just keeps the old value. Spanish usually runs longer
  than English, so translations are checked against the limit.
- **Month names need the WordPress `es_ES` language pack** installed on every
  environment; without it dates stay in English.

## 2026-10-21 — Menus per language: where Polylang keeps them

Polylang free does not translate menus as terms. Each language has its own menu
and the assignment is the option `polylang['nav_menus'][theme][location][lang]`
(`Main` for `en`, `Main ES` for `es` in `primary`). The `primary___es` location
the Customizer and the Menus screen show is a temporary label built from that
option. Polylang turns it back into the option only when one of those screens
is saved (nonce checked), so assigning it from code, REST or `set_theme_mod`
does nothing. Code sets the option through `PLL()->options->set( 'nav_menus', … )`
and saves it; the front end then ignores the theme mod for every language,
English included.

## 2026-10-21 — Playground seed in both languages

`SEED=1` now creates every item in English and in Spanish and links the pair
with `pll_save_post_translations()`: Home, the ten pages, the projects, the
services and the notes (the blocks note included). The menus `Main` and
`Main ES` are rebuilt with pages as items and assigned in the Polylang option.

- **Spanish slugs are explicit.** Pages and services use the slugs of the
  sitemap (`/es/sobre-mi/`, `/es/servicios/desarrollo-wordpress/`). Projects
  and Cookies share the English slug, so they are saved with the `-es` suffix
  and the plugin's URL layer hides it, as on the live site. Notes use a
  different slug (`nota-lorem-ipsum-1`) except the blocks note.
- **The language list is cached with the static pages in it.** The seed sets
  the front page and the posts page in the same run that builds the rewrite
  rules, and Polylang still sees the options as they were at boot, so the
  list it caches has no Spanish front page and `/es/` shows the blog index.
  The seed ends by dropping the cache; the first request rebuilds it and `/es/`
  redirects to the Spanish Home (`/es/inicio/`).
- **Stored IDs point to the same language.** A service's proof holds post IDs,
  so each language stores its own projects and notes. The Related block keeps
  the English IDs and maps them on render (see above).
- **Text is placeholder in both languages.** Titles and slugs are Spanish; the
  body is the same Lorem. No Spanish field is longer than the English one, so
  no SCF `maxlength` is hit.

## 2026-10-21 — Theme links follow the language; post types from code

- **Links to pages of the sitemap use the translation.** The theme built them
  with fixed English paths (`home_url( '/work/' )`), so a Spanish page sent the
  visitor to the English site (site title, Home sections, page templates, 404,
  service and project pages). `portfolio_theme_page_url( '/work/' )`
  takes the English path, finds that page and returns the permalink of its
  translation in the current language (`/es/trabajo/`); `'/'` is the home of the
  language (`/es/inicio/`, which skips the redirect from `/es/`). With no
  translation, or without Polylang, it returns the English path as before.
  `portfolio_theme_resolve_url()` uses it for the site paths typed in fields.
  This replaces the note in 08 that fixed paths stay English.
- **Left alone:** the Design system page, which is English only, and a path
  with several segments in a field (`/es/como-esta-hecha-esta-web/`), which is
  used as written.
- **Post types are switched on by the plugin.** `portfolio-core` adds `project`
  and `service` to Polylang's translated types with `pll_get_post_types`. It is
  checked with the `post_types` option emptied: the types stay translated, and
  without the filter they are not. An install that already has the option keeps
  working.
- **Test:** `tests/e2e/i18n.spec.mjs` checks that no internal link of a Spanish
  page (the 404 included) leaves `/es/`, and that the Spanish Home links to the
  translation of each page.
